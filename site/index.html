Pay for a GPU only while a pod is waiting for one.

Configuration for serving and fine-tuning Gemma on EKS with Karpenter, Graviton and GPU node pools, vLLM and KEDA. Taints and affinity keep each pod on the architecture its image was built for, and the repo tests that rule.

Misplace a pod. Watch the repo's own tests refuse it.

On a mixed x86 and arm64 GPU cluster, the expensive mistakes show up only as a Pending pod or exec format error. The repo checks them in tests/test_scheduling.py. That exact file runs here under pytest against the repo's real manifests in an in-memory copy. Edit a manifest or use a preset, then run the tests. Nothing is applied to any cluster.

Three pools, one architecture each

Karpenter launches nodes just in time from three NodePools. Taints and required affinity keep every workload on the architecture its image was built for.

cpuamd64, no taintdefault CPU workloads
gravitonarm64, taint arch=arm64the eval Job, multi-arch images only
gpuamd64, taint nvidia.com/gpuvLLM and training, capped at 4 GPUs, removes only empty nodes
1

Pay for GPUs only while used

Karpenter asks EC2 for a g5 or g6 node when a pod is Pending for a GPU, spot first. No node group per instance type to size.

2

Scale on queue depth

KEDA scales the model server on the vLLM queue, because a saturated GPU hides load from CPU metrics.

3

Check the fine-tune helped

A LoRA training Job writes an adapter to S3, and an eval Job compares base and tuned answers on held-out prompts.

Try it without AWS

Needs terraform 1.5+, kubectl, kubeconform, envsubst and Python 3 with pytest and pyyaml.

git clone https://github.com/gerardrecinto/gemma-karpenter-eks
cd gemma-karpenter-eks
make validate
make local        # kind cluster, arm64 host
make local-down

The design doc explains each decision, what it was chosen over and what it costs: docs/DESIGN_DECISIONS.md.

What this does not do
  • It has not been deployed to AWS, so there are no cost or latency numbers.
  • The local cluster uses a stub in place of vLLM. It proves the plumbing, not the model.
  • The scheduling tests catch the rules the repo wrote down. They do not prove a pod will fit a real instance type.
